# Policy

Kyverno enforces admission policy on this cluster today; if that changes,
update the commands below.

## Checks

- `kubectl get clusterpolicyreports,policyreports -A` — policy failures
  blocking workloads?

## Triage

- Policy deny on a new or changed workload → GitOps-fix the manifest or
  chart to comply.
- Policy audit after a Helm value change → inspect both the live workload and
  the rendered chart. A values key can be accepted but ignored by the chart.
  Do not close the issue until the affected container has the required field.
- After a Prometheus chart upgrade or hardening change, inspect the rendered
  Alertmanager, Prometheus server, and config-reloader container security
  contexts. The current chart uses
  `prometheus.alertmanager.securityContext` and
  `prometheus.configmapReload.prometheus.containerSecurityContext`.
- **`require-pdb-for-deployment` errors (not just fails) with a JMESPath
  resolution error on a vendored/generated Deployment:** the policy's
  `matchingPdbCount` context assumes every Deployment carries an
  `app.kubernetes.io/name` label. If the chart does not set one, add it to
  the pod template (additive, alongside the chart's own selector label) plus
  a `minAvailable: 1` PodDisruptionBudget — do not edit the policy itself.
- **Kyverno `require-mesh-authorization-policy` flags a Service with no
  matching AuthorizationPolicy `targetRefs`, even though a pod-`selector`
  AuthorizationPolicy already exists for the same workload:** selector- and
  `targetRefs`-based AuthorizationPolicies cover different traffic paths
  (direct ztunnel routing vs waypoint routing) and are usually **both**
  needed, not either/or — adding a `targetRefs` policy alongside the
  existing selector one is normally the fix, not replacing it. See
  `helm-charts/argocd/templates/authorization-policy.yaml` for the pattern.
- Cluster-wide policy chart change → escalate.

## Kyverno PolicyException

Grant a workload-scoped bypass from a `ClusterPolicy` with a `PolicyException`
(`kyverno.io/v2`), not a bespoke exclude-list values key on the policy
template. `helm-charts/kyverno-policy/templates/policy-exceptions.yaml` holds
platform-wide exceptions; a single workload gets its own
`<workload>-exception.yaml`. Requires `features.policyExceptions.enabled` and
`.namespace: kyverno` on the `kyverno` chart (restricts who can grant an
exception to the trusted `kyverno` namespace) — confirm this is still live on
`kyverno-admission-controller` (`--enablePolicyException=true
--exceptionNamespace=kyverno`) before assuming a `PolicyException` is honoured.

**Cover the autogenerated rule too.** A `ClusterPolicy` rule matching
`kinds: [Pod]` gets a sibling `autogen-<rulename>` rule that Kyverno
generates automatically to run the same check against the owning controller
kinds (`Deployment`, `ReplicaSet`, `DaemonSet`, `StatefulSet`, `Job`,
`CronJob`'s `autogen-cronjob-<rulename>`, `ReplicationController`). An
exception that only lists the base rule name and `kind: Pod` leaves the
autogen rule still failing. Check
`kubectl get clusterpolicy <name> -o yaml` for the autogen rule's own
`ruleNames`/`kinds` and except both. Verify with
`kubectl get polr -n <namespace>` (or `clusterpolicyreport`) — the excepted
rule should show `skip`, not `fail`.
